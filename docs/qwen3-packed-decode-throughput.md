# qwen3 packed decode + batched throughput

How the **packed (Q4) qwen3-0.6B** decode runner went from ~2× *slower* than the
F16 runner to **faster at 3.5× less weight memory**, and how the **batched /
serving throughput** path was built out on top of it — uniform *and* ragged,
packed *and* KV-resident. Every change below is **token-identical** to its
reference (validated by exact greedy-stream comparison + CPU-parity tests).

> Absolute tok/s are M4 Pro and vary with thermal/contention state (several
> measurements here were taken on a throttled machine — noted inline; the
> **ratios** and the byte/occupancy structure are the robust signals). Fresh
> single-stream packed decode is ~51 tok/s @140 ctx.

Companion doc: [`rlx/docs/metal-qwen3-decode-perf.md`](../../rlx/docs/metal-qwen3-decode-perf.md)
covers the earlier **F16-weight** single-stream path (24→89 tok/s via
F16-resident weights / split-K GEMV / weight-concat bake / GQA-native). This doc
covers the **packed Q4** path and **batching**.

---

## TL;DR

**Single-stream packed decode** (Qwen3-0.6B-Q4_K_M, Metal, token-identical to F32):

| change | tok/s @140 | note |
|---|---|---|
| packed decode before the fix | 13.6 | dense F32 `sgemm` — the routing bug |
| **+ packed routing** (emit `DequantMatMul`) | 36.0 | 2.65×; now > F16 runner (~30) |
| **+ resident KV** for native packed | 44.6 | kills O(ctx) host KV re-upload |
| **+ lm_head→F16, flash-decode P=4, warp-reduction** | **51.3** | attention 46%→23% of decode |

**Batched / serving throughput** (aggregate tok/s across concurrent sequences;
throttled ~2×, so fresh ≈ 2×):

| path | B=8 | B=16 | B=32 |
|---|---|---|---|
| uniform, F32 + host-KV | 47 | 60 (peak) | 54 (regresses) |
| uniform, **packed + resident-KV** | 62 | 91 | **91** |
| **ragged** (mixed lengths), packed + host-KV | 39 | 51 | — |
| **ragged, packed + resident-KV** | 78 | **110** | — |

The throughput axis multiplies: **batching (~4×) × packed (extends the
bandwidth→compute crossover) × resident-KV (~2× at high B)**.

## Part 1 — Single-stream packed decode

### 1.1 The routing fix — emit `Op::DequantMatMul`

Decode is weight-read-bandwidth bound, so keeping the Q4 weights *packed* (read
0.35 GB/token) instead of dequant-to-F32 (1.2 GB) should be a clear win — but the
packed runner was ~2× *slower*. Root cause: the qwen3 decode/prefill **layers
hand-rolled `gb.mm(load_param(...))`**, ignoring `opts.packed`, so the "native
packed" graph emitted dense `MatMul` → F32 `sgemm` (24 ms, 57% of decode).

Fix (`rlx-flow`): `FlowCtx::resolve_linear(key, transpose, dtype)` +
`LinearWeight::{Dense,Packed}::emit(gb, input)` — mirrors `ctx.linear`'s
`take_packed` dispatch but usable inside a live `HirMut` block. The 7 projections
in `blocks/qwen3_decode_layer.rs` + `blocks/qwen3_decoder.rs` route through it.
**Zero spec churn**: `take_packed` returns `Some` only for a packed
`WeightSource`, `None` for F32 — so non-packed builds are byte-identical.

Result: decode `sgemm ×113 = 24 ms` → `dequant_matmul_gguf ×115 = 1.79 ms`
(~13× cut). Decode became attention-bound; the packed matmul is now ~11% of the
step.

### 1.2 SIMD-cooperative quant GEMV kernels (`*_mv_f32_sg`)

The fast `q4k_mv_f32_sg` (llama.cpp `mul_mv_q4_K_f32` port: 32-thread simdgroup,
`simd_sum` reduction) was already **1.7–2.1× the F16 GEMV** (bandwidth-bound). The
other formats used **one-thread-per-row** kernels (occupancy-starved, 0.2–0.9× of
F16). Added SIMD `_sg` variants for **Q8_0, Q6_K, Q4_0, Q4_1, Q3_K** — encoders
generated by the `sg_mv_encoder!(fn, pipe, NSG, NR0)` macro
(`rlx-metal/src/backend/encode/ops.rs`), kernels in
`rlx-metal/src/dequant_gguf.msl`. All pass CPU parity
(`rlx-metal/tests/q40_q80_mv_parity.rs`). Bench:
`cargo run --release -p rlx-metal --example mps_re_bench` (quant sweep).

Speed vs the old one-thread-per-row kernel: **1.4–3.9×** (Q3_K biggest). Q8_0/Q4_K
are bandwidth-saturated (~287 GB/s ≈ peak). Notes:

- **Q4_0/Q4_1 "byte-once"**: the naive split re-read each packed byte twice (two
  lanes for low/high nibble); the `_sg` kernel reads each byte **once** and
  extracts both nibbles → ~+25% at fat-K.
- **Q3_K**: extracts only the one scale each lane needs (not all 16 per block).
- **Precision**: every `_sg` GEMV accumulates in **f32** (matches CPU <1e-3), so
  it is *more* precise than the f16-weight GEMV baseline. No precision knob needed.

### 1.3 Resident KV for native packed (kills O(ctx) host transfer)

`decode_step_gpu_resident` binds K/V to device handles and folds only the new row
each step (no host round-trip). It was F32-only (`ensure_graph_with_params`);
native packed was forced onto the host path (re-upload the padded cache every
step, O(ctx)). Fix: build the packed bucket graph via
`BucketedCompileCache::ensure_graph_with_packed` +
`build_qwen3_decode_graph_sized_packed`; the resident KV feed is graph-agnostic.
Lifted the `!is_native_packed` gate on `use_gpu_kv`. **ctx2000 packed 7.3 → 21.3
tok/s (2.9×), now > F32's 14.2.** (`generator.rs`.)

### 1.4 Attention: flash-decode default + warp reduction

After the matmul fix, attention was ~46% of decode (`sdpa_decode_m1` launches
only `batch*heads≈16` threadgroups — occupancy-starved). Two changes:

- **Flash-decode (split-KV) default-on Metal** (`RLX_METAL_SDPA_FLASH_DECODE=1`
  in `high_level_runner`) + tuned partitions to **≥64 keys/partition** (`P=4` at
  ~256 ctx). Measured sweep @256 ctx: base 6.4 ms → **P=4 3.73 ms (−42%)** → P=8
  6.1 → P=16 9.7 (combine overhead dominates large P at short ctx). Long ctx is
  bandwidth-bound, so `P` is occupancy-capped at 8 — no regression.
- **Warp reduction in the flash partial kernel** (`sdpa_decode_m1_partial`):
  replaced the threadgroup-memory tree reduction over `tg_o[32*128]` = **16 KB
  threadgroup memory** (the real occupancy limiter) with `simd_max`/`simd_sum`
  (the threadgroup is exactly one 32-lane simdgroup). Frees the 16 KB + drops the
  reduction barriers → higher occupancy. Attention **3.73 → 2.53 ms (−32%)**.

lm_head also moved to F16: `RLX_QWEN3_F16_WEIGHTS` now applies to the packed path
too (the Q4 projections ignore it — they use `take_packed` — so it converts *only*
the big tied lm_head F32→F16). GPU-time **2.6 → 1.23 ms**.

Net: attention 46% → **23%** of decode; packed decode **44.6 → 51.3 tok/s**.

### 1.5 Negative / neutral results (don't re-chase)

- **head_dim-split attention** (`sdpa_decode_m1_partial_hd`, llama
  `flash_attn_ext_vec` mapping: 8 regs/thread vs 256): built, token-identical,
  but **measured neutral** — flash already yields 64–128 threadgroups, so
  occupancy isn't register-limited at these scales. Kept **opt-in**
  (`RLX_METAL_SDPA_HDSPLIT=1`) for few-head / low-P models. The
  "register-pressure redesign" lever is disproven for this workload.
- **Concurrent dispatch** (`RLX_METAL_CONCURRENT=1`): **breaks parity** (the
  hazard `barrier_set` misses RAW/WAR/WAW cases) *and* is slower (barriers
  serialize the overlappable dispatches). Do not use.

## Part 2 — Batched / serving throughput

Decode re-reads the whole model per token, so **batching** reads the weights once
and emits B tokens: aggregate throughput scales with batch until compute
saturates. Two batched primitives, each with a stateless (host-KV) and a
**resident-KV** form, and each honoring the packed graph.

### 2.1 Uniform batched (all sequences at the same cache length)

- **Packed**: `decode_batched_uniform` builds the packed graph
  (`ensure_graph_with_packed`) when `native_packed_gguf` is set. Packed both
  raises B=1 throughput *and* pushes the bandwidth→compute crossover higher —
  F32 saturates at B=16 and *regresses* by B=32, packed keeps climbing.
- **Resident-KV**: `decode_batched_resident_init` + `decode_batched_resident_step`
  bind the `[B, upper, kv_dim]` handles once per bucket and fold each sequence's
  new token in place via **`feed_kv_batch_major_src`** (a strided-source
  generalization of `feed_kv_batch_major` — qwen3 emits the full `[B, upper+1]`
  cache, new token at row `upper`). Eliminates the O(B·ctx) per-step KV upload.
  **B=16: 55 → 91 tok/s (1.66×); B=32: 46 (host regressed) → 91 (1.98×).**

### 2.2 Ragged batched (mixed cache lengths — the real-server path)

`decode_batched_ragged` fuses sequences at *different* `past_len` (bucket = the
batch max, per-sequence RoPE + mask). Added:

- **Packed**: `build_qwen3_decode_graph_sized_ragged_packed` wired in.
- **Resident-KV**: `decode_batched_ragged_resident_init` + `_step`, using
  **`feed_kv_batch_major_ragged(src_row, src_seq_cap, dst_rows: &[usize], …)`** —
  each sequence folds into its *own* resident row `dst_rows[i] = past_len_i`
  (uniform's shared-`dst_row` feed isn't enough for ragged).

**Streams MATCH host exactly (token-identical) at every B. B=4 32→68 (2.14×),
B=8 39→78 (2.03×), B=16 51→110 (2.18×).** The resident win is *bigger* than
uniform because the ragged host pads every sequence to the batch-max and
re-uploads all of it each step — exactly what residency kills.

### 2.3 Bench

`cargo run --release -p rlx-qwen3 --features metal --example batched_decode_bench -- <weights-dir>`

Env: `PACKED=1` (packed vs F32), `RESIDENT=1` (resident vs host-KV), `RAGGED=1`
(mixed lengths + host-vs-resident correctness check), `PROMPT`, `STEPS`.

## API reference (`rlx_qwen3::Qwen3Generator`)

| method | use |
|---|---|
| `decode_batched_uniform(entries, abs_pos, past_seq)` | stateless uniform batched decode (returns advanced KV per seq) |
| `decode_batched_resident_init(caches)` / `decode_batched_resident_step(toks, abs_pos, past_seq)` | resident uniform batched decode (KV stays on device; returns logits) |
| `decode_batched_ragged(entries)` | stateless ragged (mixed-length) batched decode |
| `decode_batched_ragged_resident_init(caches)` / `decode_batched_ragged_resident_step(toks)` | resident ragged batched decode |

Resident steps keep the K/V GPU-resident and only read back the new rows to
advance an internal host mirror (for bucket rebinds). Seed once with `_init`,
then loop `_step` feeding the next tokens.

## Env-flag reference (this doc's work)

| flag | default | effect |
|---|---|---|
| `RLX_QWEN3_F16_WEIGHTS` | on (Metal) | F16-resident projections (ignored in packed — they stay Q4) + F16 lm_head |
| `RLX_METAL_SDPA_FLASH_DECODE` | on (Metal) | flash-decode (split-KV) attention; P tuned to ≥64 keys/part |
| `RLX_METAL_SDPA_FLASH_P` | (tuned) | override flash partition count |
| `RLX_METAL_SDPA_HDSPLIT` | off | head_dim-split attention partial (opt-in; neutral on 0.6B) |
| `RLX_METAL_Q{4K,6K,8_0,40,41,3K}_SG_DISABLE` | (all on) | revert a quant `_sg` GEMV to one-thread-per-row |
| `RLX_QWEN3_INPLACE_KV` | on (Metal) | first-class `Op::KvAppend` (O(1) KV append vs O(ctx) concat) |
| `RLX_QWEN3_NO_GPU_KV` / `RLX_DISABLE_GPU_KV` | off | force the host KV path (diagnostic) |
| `RLX_METAL_CONCURRENT` | off | concurrent dispatch — **broken** (parity + perf); do not use |
